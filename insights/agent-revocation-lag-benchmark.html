RevocationLag: Measuring Stale-Authority Exposure in AI-Agent Workflows

What happens when a tool permission is revoked while an AI-agent workflow is running? RevocationLag compares four authorization strategies on deterministic synthetic action traces.

Research question

How does authorization-check granularity affect unauthorized side effects after a tool permission is revoked during a multi-step workflow, and what control-event overhead accompanies each strategy?

Method

The benchmark generates 1,800 deterministic synthetic action traces using seeds 17, 29, and 43. Each trace contains benign actions, sensitive actions requiring a capability, a plan length, and a revocation point. All four policies run on the same traces.

  • check_once: checks permission at workflow start only.
  • periodic_3: re-checks every three action positions.
  • per_sensitive: checks before every sensitive action.
  • push_revoke: assumes immediate, perfectly delivered revocation notification.

Results

These are synthetic simulator results, not estimates of real-world incident rates.

In these traces, one-time authorization permits sensitive actions after revocation. Periodic checks reduce exposure but do not eliminate it. Per-sensitive-action checks block revoked actions at higher control-event counts. The push-notification baseline also blocks them with fewer events, but assumes perfect immediate delivery.

Limitations

This policy-level experiment does not execute a real agent or external tool, model prompt injection or network failures, or prove a sandbox secure. It omits concurrent actions, queued requests, retries, distributed caches, multiple capability classes, and partial failure. Results must not be generalized to deployed systems.

Reproducibility

python3 run_benchmark.py
python3 -m unittest discover -s tests -v

The package uses Python's standard library and fixed seeds. View the benchmark code on GitHub.
