Retrying fixed timeouts but not wrong answers when an agent's tools changed

AgentShiftBench: what happens to a tool-using agent when the tool changes after the agent was built.

By Muzammal Hussain · 12 November 2026 · Research update

An agent is set up against a tool, and then the tool changes: an argument is renamed, a number starts meaning something else, a write times out after it has already gone through. I built a small simulator with six mock tools and nine kinds of drift, and compared three ways an agent can react. No policy is told which drift happened; it only sees the tool's replies. Everything is synthetic, so the numbers follow from my rules and show how the mechanisms play out, not how often this happens in real systems.

Key findings

  1. Retrying helped, and also did harm: it fixed timeouts and rate limits, but every time a write had gone through before its reply was lost, retrying sent it a second time.
  2. A contract check caught most wrong answers: wrong or stale values reported as done fell from 18.5% to 3.7%.
  3. One change fooled everyone: when the tool changed what a number meant and the reply gave no sign of it, all three policies reported the wrong number. That is the whole remaining 3.7%.
  4. The check was cheap: 1.63 tool calls per task against 1.41 for plain retrying, all of the difference from re-reading the schema after a rename.

Setup

Six mock tasks (two reads, two calculations, two writes) meet nine conditions: no change, a renamed argument, a changed meaning with a version bump, the same change with no signal, stale data, 1 to 3 timeouts, 1 to 3 rate-limit errors, a write whose reply is lost, and a revoked permission. Every task and condition pair appears equally often across 5 seeds and 5,400 episodes, and each episode is run by all three policies.

  • Naive: one call, accepts whatever comes back.
  • Retry only: up to 3 attempts on timeouts and rate limits.
  • Contract guard: the same 3 attempts, plus it re-reads the schema once after an unknown-argument error, refuses replies marked stale or carrying a new contract version, sends an idempotency key with writes, and stops on a permission error.

No policy could finish a task after a revoked permission or with only stale data on offer. The difference is in what they said: the naive and retrying policies reported the stale value as the answer, while the guard reported nothing.

What this means

Retrying is not a safety measure. It is right for timeouts and wrong for writes without an idempotency key. Checking what comes back is what stops an agent from confidently reporting a wrong value, but only for changes the tool admits to. A provider that changes the meaning of a field without changing its version defeats every check that only looks at the reply, so the version number in an API contract carries real weight.

Limitations

Six hand-written mock tools and rules I chose; real APIs drift in more and messier ways. The guard is hand-coded and no language model is involved. Latency is in abstract units. Idempotency is ideal here: the server always recognises a repeated key.
